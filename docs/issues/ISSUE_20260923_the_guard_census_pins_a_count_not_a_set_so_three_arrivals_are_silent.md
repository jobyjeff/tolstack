# `DECLARED_GUARDS` pins a count, not a set, so three ways of arriving unenrolled move no number

`mutation_witness_derived_enrollment_and_gating` (2026-09-23) made *"this guard
has no witness"* computable for the three JS sources: `scripts/guard_enumeration.mjs`
scans the guard declarations, `DECLARED_GUARDS` pins how many each source has,
and `tests/test_mutation_witnesses.py::test_the_enrollment_census_holds` reddens
in under a second when that number moves. Replayed during review: planting
`await test("a planted guard nobody enrolled", …)` in `apps/viewer/tests.js`
reddens pytest naming the source and the delta, and `--unenrolled` answers with
the exact file name to write. The mechanism works and this issue is not a
complaint about it.

It is about the three arrivals it cannot see, all of which share one cause: the
pin is a **cardinality**, and the thing it is standing in for is a **set**.

## The three

1. **One guard deleted and one added in the same change.** 513 → 513. The
   deleted guard's spec, if it had one, is a loud orphan — that half works. If
   the deleted guard was unenrolled (the common case: 466 of 513 are), nothing
   moves and the new guard arrives with no spec and no signal.

2. **A new guard whose name already exists.** `enumerateGuards` deduplicates
   `(tier, name)` down to one row deliberately — two declarations of one name
   are one unattributable guard — so a second `test("<an existing name>")`
   leaves `declared` unchanged. The `enrollable` column *does* move (513 → 512),
   and the runner prints it, but nothing pins or gates `enrollable`, so the move
   is silent in `pytest -q` and in the tier's exit code. This is the same
   population `ISSUE_20260922_forty_five_browser_check_names_are_interpolated_so_no_guard_behind_them_can_be_enrolled.md`
   measures (4 of the browser tier's 31 unenrollables are names declared more
   than once); what is new here is that an *enrolled* guard can slide into it
   without anything saying so.

3. **A declaration shape the scanner does not match.** The scan requires the
   first argument to be a `"…"` or `` `…` `` literal: `test('…')` with single
   quotes, or a name handed in by a helper or a loop, is not a declaration as
   far as the enumeration is concerned. Measured 2026-09-23: there are **zero**
   such declarations in all three sources today, so this is a future hole rather
   than a present miss — but a guard written that way is invisible in both
   directions at once (not censused, so not enrollable, so never reported).

## Why it matters more than it looks

The census is now the *only* mechanism standing between a new guard and the
backlog this whole rework exists to end. Every other check in
`tests/test_mutation_witnesses.py` asks whether the specs that exist are still
true; this one alone asks whether a guard arrived without one. A gate with three
silent bypasses is still worth having — but its honest limits should be
computed, not left for the next reviewer to rediscover, the same way the
`python` hole was named in
`ISSUE_20260923_the_guard_census_cannot_see_a_pytest_guard.md`.

## The cheap half of the fix is already sitting there, unclaimed

**`declared` equals what the tier actually runs, and nothing says so.** Measured
on the merged tree, 2026-09-23:

| source | `DECLARED_GUARDS` | what the runner executed |
|---|---|---|
| `apps/viewer/tests.js` | 513 | `node apps/viewer/run_tests.cjs --repo …` → **513/513** |
| `apps/annotate/run_tests.cjs` | 154 | `node apps/annotate/run_tests.cjs` → **154/154** |

Two sources, exact agreement, twice. That agreement is the evidence the scanner
has no false positives and no false negatives today — and it is evidence a
*reviewer* produced by hand, which is precisely the shape this repo keeps
converting into a standing check. Pairing the pin against the tier's own printed
total would make the scanner's accuracy falsifiable on every run and would close
(3) outright: a single-quoted guard executes and is not counted, so the two
numbers part company.

(The browser tier is not free to pair this way — it needs a browser and several
minutes, and its `declared` is a count of distinct *names* rather than of
executed sub-checks — so this half covers the two fast tiers only.)

For (1) and (2) the cardinality has to become a set: a tracked manifest of guard
names per source, regenerated by the enumeration and diffed. That is more file
churn per guard added, which is exactly the cost the 2026-09-23 design was
avoiding, so it is a judgement call rather than an obvious yes — worth deciding
deliberately rather than by omission.

## Not urgent

Nothing is wrong in the tree today: the census holds, 115/115 mutations are
witnessed, and no guard is known to have arrived by any of the three routes.
This is the honest-limits paragraph the mechanism does not yet have.
