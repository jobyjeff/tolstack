## 1. The duplicate tooltip was TWO duplicates, not one

The handoff pins the defect on `views/nav.js`: the artifact's `description`
sits on the ROW as a native `title`, and the row also carries the alert mark,
so hovering the mark shows the row's plain tooltip under the mark's formatted
card. That is real and it is fixed (the description moved onto
`.navtree__label`).

But it is not the whole of what Jeff was looking at. `VA.alertBadge`
(`views/dom.js`) was **also** writing a native `title` on the badge itself —
the same alert sentences the card renders, unformatted — on both arms,
including the arm that wires a card. So a study row with a description had
*three* things to say on hover and two of them landed on the same pixels. The
handoff's own browser check is what surfaced it: it asks for no `title` **on
the element under the pointer** or any ancestor, and the element under the
pointer is the badge.

So the fix is in two files, and the second one is the one with reach:
`alertBadge` is worn by the nav rail AND both of `views/stack.js`'s tables, so
the rule now holds on all three. The title is kept on the no-card arm, which
is deliberate and was already a tested claim ("the information is never ONLY in
a hover" — the fast tier's bare-render check); only the arm that has a card to
absorb it loses it.

**If you are hunting a "duplicate hover" report in this app, check the badge
before you check the row.** Three surfaces can stack: the row, the mark's own
`title`, and the card.

## 2. The mark's accessible name — the a11y question the brief parked

`BRIEF_20260914_hover_card_occlusion_and_a11y.md` asks whether the nav mark has
an accessible name. The handoff asked me to record where that stands after this
change rather than decide it. Measured, not reasoned:

- The mark **has** an accessible name, and keeps it. `aria-label` was already
  set unconditionally in `alertBadge` and is untouched by this pass — on the
  live rail it reads e.g. `"pass — every build clears it unverified
  incomplete"`. Removing the `title` did not take a name with it; a `title` is
  a *fallback* name and `aria-label` already outranked it.
- What is still open is the other half: the mark is a `<span tabindex="0">`
  with **no role**. A focusable generic with a name is announced, but nothing
  says it is a button or a disclosure, and nothing says a card opened. That is
  the brief's question and it is unchanged by this change.

So the brief's premise ("the mark's accessible name") is narrower than the real
gap, and the gap that is left is `role` + the live-region question, not naming.
Filed as `docs/issues/ISSUE_20260930_the_nav_alert_mark_is_a_focusable_generic_with_no_role.md`.

## 3. The glow is the hit path, lit — and `drop-shadow` is the trap

The handoff left the technique open: "a wider, low-opacity underlay path or an
SVG `filter: drop-shadow`, your call — measure which the browser tier can
assert". Chosen: **neither, exactly.** Every rail, link and bar already carries
a transparent 10–14px twin so a 2px line can be pointed at; when the line is
hot that twin is stroked at a low alpha. A halo for one colour change, no extra
element, and `getComputedStyle(...).stroke` is a clean assertion.

`drop-shadow` was tried first in design and dropped on a real reason rather
than taste: **these are vertical lines.** A `<line x1=195 x2=195>` has an
object bounding box zero pixels wide, and a CSS filter region derived from a
zero-width box is exactly where a drop shadow is least dependable across
engines. A dot is a circle and would have been fine — but a dot is also the one
mark with no twin, so it spends width alone, which is enough because the rail
it sits on is lighting up around it.

## 4. Playwright cannot hover a vertical line, and that is the feature working

`locator.hover()` on `.rail__hit` fails with **"element is not visible"** after
a 30s timeout. Nothing is wrong: Playwright's actionability check wants a
non-empty bounding box, and a vertical line's box is zero wide; the stroke is
transparent besides. What makes the thing hoverable is `stroke-width: 14` under
`pointer-events: stroke`, which is a *paint* property Playwright does not model.

The browser tier and the debug probe both use the same shape instead: ask the
page for a point (`railPoint` — walk down the line's x asking
`document.elementFromPoint` until it answers the hit path itself), then
`page.mouse.move` there. That also proves more than `hover()` would: it is the
browser confirming the hit path is what is painted at that pixel.

Two things that bite inside `railPoint`:

- **pitch_system's DAG is taller than any viewport this runs at**, so rails
  that start below the fold have no point in the window at all. It scrolls to
  centre the rail first. Without that, 2 of pitch_system's 10 rails look
  unreachable — and which 2 depends on how far the previous block happened to
  scroll, which is a flake waiting to happen rather than a finding.
- **Restore the scroll afterwards.** Every block after it in
  `testTheTopologyPage` measures a pane at vertical zero.

## 5. Two levels of tint over two alternating bands — why `--hot` is on the CELLS

The grid's hover tint is painted on `.tvcell`, not on `.tvrow`. A row already
carries two background layers that must survive (`--tv-band-a/b` as a
background *colour*, an untraced row's provenance tint as a background
*image*), and `.tvrow:hover`'s opaque `#20242c` replaced the first of them. A
cell layer composites over both.

That also fixed a wrinkle nobody had noticed in the rule it replaced: its tint
was `#20242c`, which over this page's background is white at ≈.055 alpha —
**the same value as `--tv-band-b`**. Hovering a b-band row changed nothing at
all.

The handoff allowed dropping the lighter of the two tints if three read as
noise. Kept, but the first values were too quiet to be worth having: `--tv-hot`
started at .032 and was invisible against a b-band row in the screenshot.
Settled at .055 / .125, where the four rows of a hovered leg are legible as a
group on `pitch_system`. Judge this from the picture, not from the number — the
alternating bands mean a hot a-band row and a plain b-band row are always going
to sit close together, and the DAG lighting up beside them is what disambiguates.

## 6. Rail identity: the array index, not the column

Membership of "the whole connected line" is resolved from `layout.rails` by
**position in that array**, never by a column number. The parallel handoff
(`columns_ordered_to_minimise_crossings`) renumbers columns, and `VA.spineRight`
already mirrors every one of them at render time, so a column index is a
drawing decision rather than an identity.

A column still appears in the resolution — a row belongs to the rail drawn at
the same column over the same row span — but that is an equality between two
numbers out of the *same* layout, which survives any renumbering of both. A
fast guard plants exactly that: the demo topology with every column mirrored by
hand, asserting the same edge lights the same set.

Two details worth not rediscovering:

- A column is **reused** once a branch has ended, so the row span (not the
  column alone) is what tells two rails on one column apart.
- A **branch** curve belongs to the rail it OPENS (matched on
  `rails[i].start === link.row`, which is what tells two branches out of one
  fork apart); a **close** curve belongs to the rail its closing edge sits on.
  Resolving the branch by its `from_column` is the plausible wrong answer — it
  is the column the curve starts on and it type-checks — so it is the mutation
  that enrolls that guard.

## 7. Enrollment: 5 specs for 21 new guards, and which 5

21 guards arrived (6 fast, 15 browser). Five carry mutation specs; the other
sixteen raised the pin. The five were chosen to cover each deliverable *and*
each place a different kind of regression hides:

| spec | what it would catch |

| browser, `[real]` nav mark | `alertBadge` writing its `title` on both arms again (the shared-badge half) |
| fast, rail lights its line | a branch curve resolved to the leg it forks *out of* |

That last row is the general point: for a change that is mostly *paint*, the

## 8. Writing these files: two traps that cost time

- **The Bash tool's heredocs are not literal about backslashes.** A
  `python - <<'EOF'` script containing `"\\n"` arrives at Python as `"\n"`. That
  silently turns an anchor for the two characters `\` `n` into one for a
  newline, and the failure looks like a rotted anchor rather than a mangled
  script. Write the patch script to a file (the Write tool) and run it.
- **`scripts/guard_enumeration.mjs` is CRLF in the working tree** while most of
  `apps/viewer` is LF. A Python text-mode read/write round-trip rewrites the
  whole file's line endings; patch it as **bytes**. (That is also the file
  `LESSONS_20260930_guard_census_pins_the_set_not_the_count.md` warns can get
  its `\u0000` escapes turned into literal NULs — same class, same answer:
  don't round-trip it.)

## 9. What this change does NOT reach

- **`apps/annotate`.** It has its own rail and its own stylesheet and shares no
  CSS with the viewer by design; nothing there grew a hover state.
- **The stack page's own tables** (`views/stack.js`). They get the
  `alertBadge` half of item 1 — the mark under a card carries no native title
  there either, which is the whole-class fix — and nothing of items 2 and 3,
  because they have no rails.
- **`.tvfoot`'s total rows.** `baseRow` is only ever called with `"edge"`, so
  `.tvrow` is exactly the edge rows and replacing `:hover` cost no other row
  its feedback. If a future pass gives the footer `.tvrow` rows, they will have
  no hover tint until someone registers them.
- **Keyboard focus on the rail and link hit paths.** `hotHover` wires
  `onfocus`/`onblur` on every target, so focus drives the state for everything
  that is already focusable — bars, dots, leaders, which `wire()` gives
  `tabindex="0"`. The rail and link hit paths were deliberately **not** given a
  tabindex: they select nothing and open nothing, and ten more tab stops of
  focusable decoration on `pitch_system` is a worse a11y outcome than the one
  it would buy. A grid row (`<tr>`) is likewise not focusable, which it was not
  before either.
